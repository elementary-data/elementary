An environment is a shared-lineage container: the group of assets you want to see together in one lineage graph, because they share a production pipeline.

Everything Elementary computes — lineage, monitors, incidents, alerts, and health scores — is scoped to an environment. Each environment has its own lineage graph, built from the dependencies between the assets it contains.

## What an environment can contain

An environment is built from one or more asset sources. Each one tells Elementary which assets to sync:

- **dbt projects** — Elementary syncs models, sources, tests, and run results collected by the [Elementary dbt package](/cloud/integrations/transformation-and-orchestration/dbt-core).
- **Asset groups** — databases and schemas you select directly in the warehouse. Use these for tables and views created outside dbt, by ETL tools, orchestrators, or SQL scripts.

An environment can hold several of either kind, and can mix them. An environment built entirely from asset groups works on its own, monitored from warehouse metadata — dbt is optional.

<Note>
All asset sources in an environment currently share a single data warehouse connection. Support for several warehouse connections in one environment is coming.
</Note>

## Choosing what belongs in one environment

Put assets in the same environment when they are built by the same production pipeline, and you want to trace an issue in one through to the others.

Use separate environments when the assets belong to stacks you keep apart on purpose. Each environment is managed independently, with its own monitoring, alerts, and configuration, and you monitor all of them from a single interface.

### Development, staging and production

The most common case. If you have a single dbt project with three targets — prod, staging and dev — create three environments in Elementary, so each target has its own dashboard, alert routing, and health history.

### Intentionally segregated stacks

Some stacks are separated by design rather than by lifecycle stage, for example:

- Anonymized and non-anonymized copies of the same data
- Separate sites, regions, or tenants
- Separate products or business units

Give each one its own environment. Keeping them apart in Elementary mirrors how they are kept apart in your warehouse, so health, incidents, and lineage stay attributable to the right stack.

## Several asset sources in one environment

Connecting more than one asset source to a single environment gives teams the flexibility to organize their code by layers, domains, or separate repositories, while still getting one unified view of data health, lineage, and reliability.

Once connected, Elementary combines lineage and context across all of them, so you have a complete picture of how data flows through your stack.

### Key capabilities

- **Unified lineage across sources.** Elementary identifies assets by their full relation name, so lineage spans multiple dbt projects and asset groups with complete accuracy.
- **No changes to your dbt structure.** Each dbt project keeps its own models, sources, repository, and Elementary schema. Elementary handles the unification at the environment level.
- **Automatic linking between sources and models.** If the same relation appears as a model in one project and a source in another, Elementary displays two nodes in lineage with a clear link between them. This makes dependencies explicit and helps you trace issues further upstream.

### When to use several asset sources

This is designed for teams whose production pipeline spans more than one project or tool, such as:

- Layered architectures (bronze, silver, gold)
- Domain-based modeling (finance, marketing, operations and others)
- Multiple dbt projects built on the same raw data
- Pipelines stored in separate repositories
- Tables loaded by ETL tools or scripts alongside dbt models

<Note>
Each dbt project added to an environment must use a different Elementary schema, and the Elementary dbt package must be installed in each project. Asset groups work straight from warehouse metadata, so they need neither.
</Note>

## Setting up an environment

1. Go to **Account settings > Environments** and click **Create environment**.
2. Give the environment a name.
3. Connect the [data warehouse](/cloud/integrations/elementary-integrations) the environment reads from.
4. Click **Continue** to reach the environment content section, and add the asset sources this environment contains — dbt projects, asset groups, or both.
5. Save. Elementary begins syncing, and a backfill collects historical metadata so monitors have a baseline.
